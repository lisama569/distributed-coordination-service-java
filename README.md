# 本地可验证的分布式协调服务（Java / Spring Boot）

一套**完全在单个 JVM 进程内**运行、用模拟时钟与模拟网络复现“集群 / 网络分区 / 进程崩溃”
的分布式协调服务，不依赖任何外部中间件或真实网络服务。实现并可解释地验证三件事：

1. **基于多数派的领导者选举与任期管理**（Raft 变体 + 领导者租约）；
2. **带租约与栅栏令牌（fencing token）的分布式锁**；
3. **幂等执行与崩溃恢复**（检查点 + 重放，拒绝任期/位点回退）。

所有行为由一个全局模拟时钟按 1ms 步长确定性推进，单线程 tick，结论可复现。

## 2. 选举与租约模型

### 2.1 选举（多数派 + 任期）

- 节点角色：`FOLLOWER / CANDIDATE / LEADER`；多数派 = `floor(n/2)+1`，3 节点为 2。
- 跟随者在 `[180,300]ms` 的**确定性随机选举超时**内未收到有效领导者心跳即成为候选者，
  任期号 `+1` 并向其他节点拉票；日志必须“至少一样新”才能得到选票。
- 得票达到多数派即成为领导者，任期号**单调递增，绝不回退**：
  任何节点见到更高任期的 RPC 都会结束候选/领导状态并更新任期。
- 选举超时按节点身份 + 落选轮次做固定种子抖动：不同节点错开、落选后重新抖动，
  避免反复撞票活锁；种子固定，测试结果可复现。

### 2.2 领导者租约（为什么不会双主）

- 领导者当选时获得一个时长 `leaderLeaseMillis`（默认 400ms）的租约；
  此后**只有收到多数派的心跳应答**才能把租约续到 `now + lease`。
- 心跳中携带“领导者租约到期提示”。跟随者/候选者在**已知旧领导者的租约到期之前
  不会投出任何选票**。
- 关键不变式：`leaderLeaseMillis > electionTimeoutMaxMillis`（400 > 300，构造时强制校验）。
  因此任何新领导者的当选时刻必然晚于旧领导者租约的到期时刻——
  **同一时刻至多存在一个被多数派承认的领导者**。
- 旧领导者被隔离进少数派后无法再收集多数派应答，租约必然到期：
  - 它**保留 LEADER 角色直到见到更高任期**，因此写请求得到的错误可以精确区分：
    租约过期 → `LEADER_LEASE_EXPIRED`；根本不是领导者 → `NOT_LEADER`。
  - 分区恢复后它收到新任期的 AppendEntries，立即降级为跟随者并接受新任期，
    **不会出现双主，也不会用旧任期覆盖新任期**。
- 读同样要求“是领导者且租约有效”。

### 2.3 日志复制与提交

- 写请求由领导者追加到本地 Raft 日志并即时复制（模拟网络可靠、即时投递）；
  多数派落盘后推进提交位点，状态机按序应用。只提交当前任期的条目（标准 Raft 规则）。

## 3. 锁、租约与栅栏令牌

### 3.1 栅栏令牌编码

```
FenceToken = (term << 20) | sequence
```

- `term` 为颁发令牌时的领导者任期，`sequence` 为该任期内单调递增的序号；
- 令牌整体**随任期单调递增**：任期变大时令牌必然更大，同任期内只增不减；
  比较先比任期、再比序号。

### 3.2 获取 / 续期 / 释放

- **获取**：锁不存在或租约已过期才能获取；成功时由领导者分配新栅栏令牌，
  锁记录 `(持有者, 令牌, 租约到期时间)`。锁仍被有效持有时竞争失败。
- **续期**：必须同时满足“持有者匹配 + 令牌不旧 + 提议时租约仍有效”，缺一不可。
- **释放**：持有者匹配且令牌不旧即可（令牌匹配本身就代表最新授权）。
- 租约有效性以**日志中固化的提议时刻** `proposedAt` 判定，而不是应用时的墙钟：
  旧持有者在租约失效后才复制到各节点的“迟到写”在每个节点上都会被一致拒绝，
  重放结果也完全确定。

### 3.3 三类可区分的拒绝原因

| 原因码 | 触发条件 |
| --- | --- |
| `LOCK_NOT_HELD` | 竞争失败（锁仍被他人有效持有）/ 锁不存在 / 持有者不匹配 |
| `LOCK_LEASE_EXPIRED` | 令牌是当前令牌，但发起操作时锁租约已过期（含迟到写、过期后续期） |
| `STALE_FENCE_TOKEN` | 携带的栅栏令牌比锁当前令牌更旧（fencing，旧持有者迟到写） |

存储侧写 KV 时顺序判定：先查锁是否存在 → 再比令牌新旧 → 再查租约，
因此“令牌过旧”和“租约过期”不会被混为一谈。

领导者侧另有 `NOT_LEADER` / `LEADER_LEASE_EXPIRED` / `NO_LEADER`，
恢复侧另有 `ROLLBACK_REFUSED`。

## 4. 幂等与崩溃恢复语义

### 4.1 幂等（同一键只产生一次写入效果）

- **每个写请求都必须带幂等键**。三层防线：
  1. `CoordClient` 进程内在途表：同一幂等键的并发提交直接抑制；
  2. 领导者在途去重：同一幂等键已有未提交日志时不再追加第二条；
  3. **复制状态机幂等表（最终防线）**：幂等键 → 已确定结论（含拒绝结论）。
     重试、换领导者、跨任期重复提交都复用同一结论。
- 拒绝也是结论：例如抢锁失败后用同一幂等键重试，永远得到同一个
  `LOCK_NOT_HELD`，不会意外建出第二把锁。

### 4.2 崩溃恢复

- 节点在「投票 / 追加日志 / 提交应用」后把检查点原子写入
  `{checkpointDir}/{nodeId}.checkpoint.json`（临时文件 + 原子 rename，崩溃不留半写文件）。
- 重启时新建节点实例并 `restore()`：加载检查点后从空状态**重放已提交日志**
  重建锁表/KV/幂等结论。重放是初始化而非重复应用——已提交操作只生效一次，
  未提交条目不会被应用。
- 安全门 `CheckpointStore.ensureNoRollback` / `RaftNode.restoreFrom`：
  试图用**任期更旧、日志更短或提交位点更小**的检查点启动时，直接抛出
  `ROLLBACK_REFUSED` 并拒绝继续执行。

## 5. 可配置项（`application.properties`，前缀 `coord.`）

| 配置项 | 默认值 | 含义 |
| --- | --- | --- |
| `coord.cluster-size` | `3` | 集群节点数（建议奇数） |
| `coord.heartbeat-interval-millis` | `50` | 领导者心跳间隔（模拟毫秒） |
| `coord.election-timeout-min-millis` | `180` | 选举随机超时下限 |
| `coord.election-timeout-max-millis` | `300` | 选举随机超时上限 |
| `coord.leader-lease-millis` | `400` | 领导者租约时长（必须 > 选举超时上限） |
| `coord.lock-lease-millis` | `250` | 锁租约默认时长 |

单测直接用 `SimTimers(50,180,300,400)` 与临时检查点目录构造 `Cluster`，
不需要启动 Web 服务或任何外部进程。

## 6. 本地验证方法

前置：JDK 21+、Maven（依赖可离线解析）。

```bash
# 运行全部测试（无需数据库 / 网络 / 中间件）
mvn test

# 只运行某一组场景
mvn -Dtest=LeaderElectionTest test            # 选举、任期单调、少数派不可选主
mvn -Dtest=LockFenceTest test                 # 竞争失败 / 租约过期迟到写 / 旧令牌 fencing
mvn -Dtest=IdempotentRecoveryTest test        # 幂等重试 / 崩溃重启恢复 / 回退拒绝
mvn -Dtest=ConcurrentIdempotencyTest test     # 多线程同键并发只写一次 / 跨任期令牌单调
mvn -Dtest=PartitionRecoveryScenarioTest test # 端到端：分区→旧主失效→新主→恢复→无覆盖
```

测试会在控制台 / surefire 报告中打印每个关键判定的
**任期、栅栏令牌、幂等键与判定依据**，例如：

```
[状态机] LOCK_ACQUIRE 拒绝: 幂等键=acquire-B, 任期=1,
  令牌=FenceToken(term=1,seq=2,...), 原因=LOCK_NOT_HELD,
  依据=锁仍被 holder-A 有效持有至 450
[状态机] KV_WRITE 拒绝 ... 原因=STALE_FENCE_TOKEN / LOCK_LEASE_EXPIRED（可区分）
[选举] 节点=n2 ... 成为领导者: 任期=3 ...；旧主恢复后降级为 FOLLOWER
[检查点] 拒绝任期/位点回退: 节点=n1, 任期 已持久化=3, 试图恢复为=2
```

### 6.1 测试场景与预期结论对照

| 场景 | 注入手段 | 预期结论 |
| --- | --- | --- |
| 双主防护 | 旧领导者单独分区 | 旧主租约到期后写 → `LEADER_LEASE_EXPIRED`；多数派选出更高任期新主；`Cluster.leader()` 永远至多一个 |
| 租约过期迟到写 | 不续期推进时钟 | 当前令牌 → `LOCK_LEASE_EXPIRED`；旧令牌 → `STALE_FENCE_TOKEN` |
| 令牌过旧 fencing | B 在 A 失锁后获新令牌 | A 持旧令牌写 → `STALE_FENCE_TOKEN`，KV 不被覆盖 |
| 分区恢复 | `split(...)` 后 `heal()` | 旧主降级、任期追平；旧任期不覆盖新状态 |
| 重复提交 | 同幂等键连写 3 次不同值 | 仅第一次生效，后续复用结论 |
| 崩溃恢复 | `crash()` + `restart()` | 已提交数据不丢、不重复应用；旧键重试无第二次效果 |
| 回退检查点 | 用更旧的检查点 `restoreFrom` | `ROLLBACK_REFUSED`，拒绝启动 |

## 7. 模型边界（诚实说明）

- 这是**教学/验证用的进程内模拟**：网络即时、可靠、不重排消息，没有真实 RPC 超时与并发线程；
  时间只能由模拟时钟前进。它验证的是算法在“分区 + 租约时间 + 多数派”下的**安全结论及其可解释性**，
  不是生产级 Raft 实现。
- 日志复制与检查点在真实系统中需要独立的持久化与 flush 时机；这里以“方法返回即已持久化”建模。
