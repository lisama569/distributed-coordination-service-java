# 分布式协调服务（本地可验证）

一个**完全在进程内**运行、用本地测试即可验证的分布式协调服务：用可控逻辑时钟模拟时间、
用方法调用模拟 RPC、用对象生命周期模拟崩溃与恢复，**不依赖任何外部中间件、网络或多线程**。
提供五件能力：

1. 基于多数派的**领导者选举与任期管理**（Raft 风格）；
2. 带**租约与栅栏令牌（Fencing Token）**的分布式锁；
3. **幂等执行与崩溃恢复**（去重表 + 检查点/日志重放）；
4. **历史压缩（Log Compaction）**：**默认开启**（阈值 100，可配/可关），持续写入时
   自动把已落定历史压成紧凑存档并真正回收旧日志；恢复/新建先装存档再补增量，
   结果与从头重放一致；
5. **滞后节点追赶（Catch-up）**：长时间失联/新加入/换过主的节点靠冲突提示
   **常数轮**（纯滞后 1 轮、存档+增量 ≤2 轮，轮数不随落后多少变长）补齐，
   追赶期间集群照常写入；掉队超出可恢复窗口时被明确挡回，不假装追平。

结论在双主、租约过期、分区恢复、重复提交、历史压缩、掉队超窗等场景下保持一致且可解释
——每个失败都被显式归类为一种 `CoordinationErrorCode`，日志中打印任期、位点、
幂等键、栅栏令牌与判定依据。

## 2. 选举与租约模型

### 2.1 选举（多数派 + 单调任期）

- 节点角色：`FOLLOWER / CANDIDATE / LEADER`。
- 选举超时（带每节点确定性扰动，避免同时拉票）未收到合法领导者心跳时，
  候选者 `term + 1`、先投自己、再向其余节点拉票；得到 **多数派（N/2+1）** 票即当选。
- **同一任期一票**：节点在一个 term 内最多投一次，且只投给日志至少和自己一样新的候选者，
  因此**同一任期至多产生一个领导者**，从机制上杜绝双主。
- 任何 RPC 见到更高 `term` 都立即退让为 follower；`term` 只升不降。

### 2.2 领导者租约（Lease）

- 领导者每 `heartbeat-interval-millis` 发一轮心跳（空 AppendEntries）。
- 一轮心跳得到**多数派 ACK**，就把自己的租约续到 `now + lease-ttl-millis`。
- 写请求（`RaftNode.propose`）只在 `role=LEADER` 且 `now <= 租约到期` 时被接受：
  - 被分区隔离、拿不到多数派 ACK → TTL 后无法续约 → 写被拒绝；
  - 收到更高任期 → 立即下台 → 写被拒绝。
- 日志复制同样走多数派：新条目复制到多数派后推进 `commitIndex`，
  且遵循 Raft 安全约束（只直接提交当前 term 的条目），随后按序应用到状态机。

### 2.3 分区恢复为何不会双主 / 旧任期覆盖新任期

- 被隔离的旧领导者在 TTL 后失去租约，不再接受写；多数派一侧会选出**更高 term** 的新领导者。
- 分区恢复后，旧领导者收到新领导者更高 term 的心跳/响应，立即转为 follower 并追上任期，
  不可能再以旧 term 写入。集群层 `ClusterSimulator.leader()` 若同时发现两个
  “有有效租约的领导者”，会直接抛出内部错误（该情况在设计上不应发生）。

## 3. 租约锁与栅栏令牌

`LockService` 只在“当前领导者且其租约有效”时颁发锁：

- **栅栏令牌** = `(term, seq, holderId, lockName)`。`seq` 是该任期内的颁发序号，
  令牌比较先看 `term` 再看 `seq`；因此换任期后新锁令牌严格大于旧锁令牌（单调递增）。
- 获取：目标锁无“租约内的持有者”才成功；否则返回 `LOCK_CONTENDED`。
- 续期：令牌匹配且在租约内才成功并把到期时间推后一个 TTL。
- 释放：仅当前持有者（令牌匹配、未换代、未过期）可释放；释放后保留栅栏代次记录。
- **迟到写防线** `validateWriteToken(lock, token, now)`：
  - 锁已被更高令牌持有者拿走 → `STALE_FENCE_TOKEN`；
  - 令牌匹配但 `now > 到期时间` → `LEASE_EXPIRED`；
  - 无持有者记录 / 被他人持有 → `LOCK_CONTENDED`。

三类失败互斥、可区分，测试中逐一断言。

## 4. 幂等与恢复语义

### 4.1 恰好一次写入效果

- 写请求带 `idempotencyKey`。`WriteCoordinator.submit` 在提交前先查内存去重表：
  - 未命中 → 调 `RaftNode.propose` 走多数派提交，落日志后记录 `(key → term/index/value)`；
  - 命中 → 直接回放**首次**提交的结论（`dedupHit=true`），不再产生日志。
- 因而**重试、重复提交、同 tick 内的并发交叠提交**，最终都只有一条日志、一次写入；
  重试即使携带不同的值，也以首次提交值为准。

### 4.2 崩溃恢复

- `InMemoryDisk` 扮演节点本地磁盘：`crash(node)` 只丢弃节点的内存对象（RaftNode、
  协调器、状态机），磁盘上的**检查点与日志保留**。
- `restart(node)` 用同一块磁盘重新组装：
  - `RaftNode.recover()` 恢复 `currentTerm / votedFor`，并把已提交日志按序重放到
    一个全新状态机；`KvStateMachine` 以日志位点去重，**重复应用同一位点不产生重复效果**；
  - `WriteCoordinator.restore()` 扫描日志重建幂等去重表，重启后的重试依旧只回放、不二次写入。

### 4.3 回退显式拒绝

下列情况都抛出 `CHECKPOINT_ROLLBACK`，而不是静默继续：

- 检查点 `currentTerm` 变小（任期回退）；
- 检查点 `lastIndex / appliedIndex` 变小（位点回退）；
- 日志非连续追加或新日志 term 小于旧日志 term；
- 状态机被要求应用小于已应用位点的下标；
- 存档位点/任期回退、截断未被存档覆盖的日志、安装更旧的存档。

## 5. 历史压缩与滞后节点追赶

### 5.1 默认触发规则与保留窗口

- 磁盘历史由两部分组成：**一份存档 `Snapshot`**（覆盖 `1..lastIncludedIndex` 的
  已提交应用状态）+ **存档之后保留的增量日志**（下标从 `lastIncludedIndex+1` 开始）。
- **默认交付即开启压缩**：规模阈值 `coordination.compaction-threshold-entries`
  默认 `100`。每当存档之外堆积的**已应用**增量达到该条数，就把更老的历史压成存档，
  并始终在存档之外**保留阈值数量的最新增量**。因此默认配置下写入持续累积时：
  - 较早的已落定历史会被持续整理成紧凑存档，被覆盖的旧日志前缀被真正删除回收，
    磁盘/日志规模稳定压在阈值附近、不再随写入无限上涨；
  - 正在提交/返回的当条绝不会被截断；
  - 落后在"保留窗口"（阈值条增量）内的节点仍能用增量日志直接追上，不必重装存档。
- 显式把阈值设为 `<=0` 才关闭压缩（仅用于对比或特殊场景）；集群模拟侧可用
  `new ClusterSimulator(n)` 直接得到同样的默认行为。
- 压缩只在状态机真实 `apply` 之后发生。存储层还有一道硬校验：**存档位点不允许超过
  已应用位点**，任何尚未确认生效的内容都进不了存档（违反即 `CHECKPOINT_ROLLBACK`）。

### 5.2 存档内容与"等价于完整重放"

`Snapshot` 只包含已落定生效的内容：

- `lastIncludedIndex / lastIncludedTerm`：存档覆盖的最后位点及任期；
- `currentTerm`：制作时已知的最大任期（单调递增）；
- `data`：状态机在该位点的**全量** K/V；
- `idempotent`：该位点（含）之前**全部已生效幂等写**的索引
  `idempotencyKey -> (term, index, value)`。

节点崩溃恢复或空盘新建时：**先整体安装存档**（状态机与幂等索引一次性到位点 N），
**再补 N 之后的增量日志**。因此：

- 最终状态、幂等结论与"从 index=1 完整重放全部已提交日志"**严格一致**；
- 已承诺生效的写入一条不丢（幂等索引随存档保留），未确认生效的内容一条不算。

### 5.3 滞后节点追赶（InstallSnapshot + AppendEntries）

- 领导者心跳时维护每个对端的 `nextIndex/matchIndex`。当对端需要的下一批增量**在领导者
  本地已被压缩到一条不剩**（`nextIndex <= 领导者 snapIndex`）时，改发 `InstallSnapshot`；
  对端装完存档后，后续位点继续走 `AppendEntries` 补增量。
- **一轮跳到分叉点（常数轮追赶，不随落后多少变长）**：跟随者拒绝 AppendEntries 时，
  在响应中携带冲突提示 `conflictTerm / conflictIndex / peerSnapIndex`：
  - 纯缺日志（自己更短/有空洞）→ 告诉领导者自己的日志尾，领导者**当轮**把 `nextIndex`
    跳到该位点之后，下一轮一次性补齐整段缺失增量；
  - 任期分叉 → 告诉领导者冲突任期在自己本地的首条位点，领导者跳到该任期最后一条之后，
    至多两轮对齐；
  - 所需位点已被本地存档覆盖 → 提示领导者改推存档。

  旧实现每轮只把 `nextIndex` 回退一格，掉线越久、落后越多，追赶轮数线性增长；
  改造后纯滞后 **1 轮**、分叉 **≤2 轮**、空盘重置（存档+增量）**≤2 轮**，
  且轮数与落后条数无关（测试中 50/200/500/2000 条落后均为常数轮，详见
  `DefaultCompactionAndFastCatchUpTest`）。
- **追赶不阻塞写入**：复制是异步收敛的，多数派由其余健康副本凑齐，掉队者追赶期间
  集群照常接受并提交新写。
- **同一次写不会算两遍**：状态机按日志位点幂等应用，存档是整体替换（不逐条重放），
  增量按位点严格续接；已在存档里生效的幂等键，补齐后重试直接回放结论，不推进应用位点。
  测试用 `replayApplyCount()==0`（绝无同位点重复应用）+ 最终状态逐键比对双重断言。
- 领导者用"成员代次（incarnation）"识别**重置后重加入**的同名节点：代次变化即丢弃
  该对端旧的复制进度，从存档重新同步（本地有存档时当轮直接推 InstallSnapshot），
  避免拿陈旧 `nextIndex` 对空盘发增量。该代次记忆跨领导者任期保留，健康对端换主后
  第一次心跳按乐观位点探测，不会被误推存档。

### 5.4 可恢复窗口边界（不假装追平、不从中间续写）

**可恢复窗口的口径**：集群当前能为掉队节点提供的最早服务位点 = 在任领导者存档位点
`leaderSnapIndex + 1`（该位点之前的原始日志已被压缩删除，只能靠整份存档补齐）。

- 节点**落后但自带历史仍连续**（纯滞后、或分叉点仍在领导者保留的增量范围内）→
  走 5.3 的冲突提示快速增量对齐，**不是**超窗；
- 一个**自带存档覆盖范围之外旧历史（含未获多数派确认的本地分叉尾巴）**的节点，
  若它缺的增量已被集群压缩（领导者只能提供一份会抹掉其旧历史的存档），安装请求会被
  **明确拒绝**，原因 `OUT_OF_RETENTION_WINDOW`；
- 系统既**不覆盖**它的旧历史，也**不允许**它从某个中间位置悄悄续写、更不会把它
  标记成已追平；领导者侧可通过 `RaftNode.blockedCatchUpPeers()` 查询被挡回的节点
  及原因（该原因与"正常竞争失败/不是领导者"明确可区分）。被挡回期间领导者不再向其
  重复推送，也不会把它计入 ACK，但集群写入与多数派提交不受任何影响。
- 该类节点的唯一合法恢复路径是**显式重置本地磁盘后重新加入**
  （`ClusterSimulator.rejoinWithReset`）：空盘 -> 安装存档 -> 补增量，常数轮追平后
  挡回标记自动清除，重新正常参与多数派。
- 若节点只是装过一份稍旧的存档、尚无存档之外的分叉增量，则允许它就地更新到领导者
  的更新存档（同属正常追赶），不会被误判为超窗。

### 5.5 追赶大概要多久

以心跳轮为单位（一轮 = 一个 `heartbeat-interval-millis`），与落后条数基本无关：

| 掉队形态 | 补齐轮数 |
| --- | --- |
| 纯滞后（自带连续历史，缺的增量仍在领导者保留窗口内） | **1 轮**（冲突提示一轮跳转，下一轮整段补齐） |
| 任期分叉（分叉点仍在领导者增量范围内） | **≤2 轮** |
| 空盘新加入 / 超窗后显式重置（需 InstallSnapshot） | **≤2 轮**（1 轮装存档 + 1 轮补尾部增量） |
| 自带旧历史且所需位点已被压缩 | **不追赶**：明确挡回 `OUT_OF_RETENTION_WINDOW`，必须重置 |

追赶期间领导者写入与提交全程不停；上述轮数是"重新正常参与多数派（matchIndex 追平）"
的时间，测试里 200/2000 条落后实测均为 1～2 轮。

### 5.5 对既有语义的兼容（保持不变）

- **选举/任期/租约**逻辑完全不变；压缩只影响日志存储与追赶通道。
- **幂等恰好一次**：压缩前、压缩后、压缩后重启、换主后重试，同一幂等键都只产生一次
  写入效果——协调层以接收节点的**已应用幂等索引（存档 + 增量）**为权威依据，重试以
  首次提交值为准。
- **租约锁/栅栏令牌**：锁持有关系是独立的领导者内存状态，不参与日志压缩；仍在有效
  租约内的持有关系不会因压缩中断，`LOCK_CONTENDED / LEASE_EXPIRED /
  STALE_FENCE_TOKEN` 的区分不变，令牌落后或租约过期的写依旧被拒。

## 6. 错误归类（`CoordinationErrorCode`）

| 错误码 | 触发场景 |
| --- | --- |
| `NOT_LEADER` | 非领导者节点接受写 / 颁发锁，或写入过程中被更高 term 赶下台 |
| `NO_QUORUM` | 选举或写入无法获得多数派 |
| `LEASE_EXPIRED` | 领导者租约过期后继续写，或锁持有者租约过期后的续期/迟到写 |
| `LOCK_CONTENDED` | 锁仍被其他持有者在有效租约内持有 |
| `STALE_FENCE_TOKEN` | 旧任期/旧代次令牌用于写或释放，锁已被更高令牌持有者拿走 |
| `STALE_TERM` | 请求任期落后于节点当前任期 |
| `CHECKPOINT_ROLLBACK` | 任期/日志位点/应用位点/存档位点回退、非连续追加、截断未存档日志、压缩未应用内容 |
| `OUT_OF_RETENTION_WINDOW` | 节点自带存档之外旧历史、所需增量已被集群压缩：不覆盖不续写，必须显式重置后以存档+增量重加入 |

## 7. 可配置项

`src/main/resources/application.properties`（时间项均为**逻辑毫秒**，非真实时间）：

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `coordination.node-count` | `3` | 模拟集群节点数 |
| `coordination.election-timeout-millis` | `100` | 选举超时 |
| `coordination.heartbeat-interval-millis` | `30` | 领导者心跳间隔 |
| `coordination.lease-ttl-millis` | `60` | 领导者/锁租约 TTL |
| `coordination.compaction-threshold-entries` | `100` | 历史压缩规模阈值：存档外每堆积多少条**已应用**增量就压缩一次，并始终保留该数量最新增量；**默认即开启**，持续写入时旧日志被稳定回收；`<=0` 显式关闭压缩 |
| `coordination.run-demo-on-startup` | `false` | 启动时是否演示五个场景 |

## 8. 本地验证方法

### 8.1 单元测试（推荐）

```bash
mvn test
```

覆盖七组共 31 个用例，全部确定性可复现：

- `LeaderElectionTest`：同任期唯一领导者；隔离领导者→失多数派/租约过期→拒绝写；
  多数派选出更高 term 新领导者；分区恢复无双主、旧任期不覆盖新任期；多轮改选任期单调。
- `LeaseLockTest`：`LOCK_CONTENDED` / `LEASE_EXPIRED` / `STALE_FENCE_TOKEN` 可区分；
  TTL 内续期成功、TTL 后迟到写被拒；新任期令牌严格更大，旧令牌写与释放都被拒；
  follower 不能颁发锁。
- `IdempotencyRecoveryTest`：重试/并发重复提交只有一次写入；崩溃重启从检查点恢复、
  不重复应用；旧任期迟到写在落盘前被拒且不留痕、副本在领导者崩溃后仍保有已提交数据；
  任期/位点/应用位点回退被显式拒绝。
- `LogCompactionCatchUpTest`：压缩后状态/幂等索引与完整重放一致、旧日志前缀被删除；
  失联节点靠存档+增量补齐、追赶期间照常写入且同一写不重放两遍；**压缩后重启**先装
  存档再补增量；**换主后重试**旧幂等键仍只回放一次；**超窗节点**被
  `OUT_OF_RETENTION_WINDOW` 明确挡回、重置后才追平；压缩期间有效租约锁不中断。
- `DefaultCompactionAndFastCatchUpTest`（本轮加固的核心回归）：
  - **默认配置**（不显式开任何开关）持续写入即触发压缩，存档持续推进、旧日志真正回收，
    存档外增量稳定有界，且所有节点（不只领导者）都被压缩；
  - 掉线很久且**期间换过两任主**、落后 200+ 条的节点，**少数几轮**即追平（轮数不随
    落后变长），追赶期间新写入照常提交、同一写不被算两遍、旧幂等键重试只回放；
  - 超出可恢复窗口的崩溃节点**显式重置**后以存档+增量常数轮追平；
  - 持有**未获多数派确认的分叉尾巴**、且分叉位点已被集群压缩进存档的节点被
    `OUT_OF_RETENTION_WINDOW` 明确挡回（与正常竞争失败可区分），重置后才追平，
    幽灵写绝不生效；
  - 同一幂等键在"先压缩后换主重试"与"先重试后压缩再换主重试"两种时序下都只生效一次；
    换主+压缩后旧栅栏令牌的迟到写仍被 `STALE_FENCE_TOKEN` 拒绝。
- `SnapshotStorageTest`：存档位点/任期不回退；未应用内容禁止进存档；只截断已被存档
  覆盖的前缀；安装存档后增量可从存档位点之后续接。
- `SmokeTest`：基本选举冒烟。

测试日志会打印 **term、位点（snapIndex/appliedIndex）、幂等键、栅栏令牌、判定依据**，例如：

```

[idempotent node=node2] 幂等键=bulk-1 命中已生效记录 index=1 term=1 (依据: 节点已应用索引/存档) -> 直接回放，不重复写入
[scenario-超窗挡回] node2 被在任领导者 node3 明确挡回: ... (判定依据: OUT_OF_RETENTION_WINDOW，不覆盖旧历史、不从中间位点续写)
```

## 9. 模拟手段与边界说明

- **逻辑时钟**：`SimClock` 只能单调向前推进，所有节点共享；测试用 `cluster.advance(n)`
  精确制造“TTL 到期”“选举超时”，杜绝真实 sleep 的抖动。
- **网络分区**：`isolate(node)` 让该节点与其余节点双向不可达，RPC 返回空（视作超时）；
  `healPartition()` 恢复连通。
- **崩溃**：`crash(node)` 删除节点内存对象、保留 `InMemoryDisk`；`restart(node)` 重建，
  先装存档再补增量。
- **重置重加入**：`rejoinWithReset(node)` 模拟掉队超窗后的运维动作——清空节点本地
  历史（成员代次 +1），领导者识别后以存档+增量把它重新补齐。
- 为保持实现精简，本模拟是**单线程同步**的：选举/复制/压缩/追赶在一次 tick 或一次写
  调用内完成，不模拟真实网络乱序、磁盘 fsync 延迟与拜占庭故障；但选举安全性、租约失效、
  栅栏令牌、幂等去重与"只压缩已生效历史、超窗明确挡回"的判定逻辑与真实 Raft/租约系统一致。
